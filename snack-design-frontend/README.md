# snack-design-frontend · 食有数Bite微信小程序

基于用户交付的「食有数-定版交付」HTML 原型开发，原生 WXML / WXSS / JavaScript。当前已连接同级 `snack-design-backend` Java 后端，未提交草稿仍只存本机。

## 目录与导入

前端使用 `D:\wtt\小程序\snack-design\snack-design-frontend`，后端使用 `D:\wtt\小程序\snack-design\snack-design-backend`。

当前 `snack-design` 是包含前后端的仓库根目录，微信开发者工具只导入其中的 `snack-design-frontend`。不要按旧的目录迁移说明删除根目录；后续前端改动只维护该子目录。

本轮保留了已有小程序 AppID，不需要重新填写测试 AppID。服务端正式微信登录仍需要独立配置 AppSecret，绝不能放到小程序中。

## 启动联调

### 1. 启动DeepSeek后端

当前使用用户已选择的DeepSeek付费API：官方Search/Fetch检索网页，再由DeepSeek模型总结，不需要Docker、SearXNG、Ollama。按后端 `DEEPSEEK.md` 在 `.env` 或环境变量配置 `DEEPSEEK_API_KEY`，运行 `start-deepseek.cmd`。搜索/抓取与模型推理会分别消耗账户额度；不要把Key放入小程序或聊天。

必须先在旧Java窗口按Ctrl+C释放8080，再从后端新目录启动。健康检查应包含 `apiVersion:3`，否则仍是旧运行版本。

仅需单独启动Java时：

```powershell
cd D:\wtt\小程序\snack-design\snack-design-backend
mvn spring-boot:run
```

或双击后端的 `start-local.cmd`。保持窗口打开，浏览器访问 `http://127.0.0.1:8080/api/health`，应显示 `{"status":"ok"}`。

### 2. 再启动小程序

1. 微信开发者工具导入 `snack-design-frontend`。
2. 「详情 → 本地设置」勾选「不校验合法域名、web-view（业务域名）、TLS 版本以及 HTTPS 证书」，仅用于本地开发。
3. 点击编译，无需构建 npm。
4. 首页“试一包”直接离线查看预设demo；真实流程请用“手动输入配料表 → 确认上传 → 自动查询 → 查看记录”。

`utils/config.js`：

```javascript
module.exports = {
  baseUrl: 'http://127.0.0.1:8080/api',
  authMode: 'dev'
}
```

本地模式自动申请测试会话，不代表生产微信身份认证。关闭后端后，读取/保存会显示网络错误，不会静默回退本机记录，避免两套数据混用。

## 首页示例体验（不依赖后端）

首页“第一次用？先试一包”的燕麦脆饼卡片现在直接打开已经填充的示例配料表与分组解析，不再进入输入页。提供原味5项、可可味6项、坚果味6项三份预设虚构配方，页面顶部可切换。

示例无需登录、联网、Java后端或AI模型，不保存到用户记录、不改写草稿，也不冒充实时AI查询。来源标为演示参考，食用建议明确为预设演示。数据位于 `utils/demo.js`，与 `utils/records.js` 的真实接口流程隔离。

## 底部导航与扫码动作

底部使用 `custom-tab-bar/`，显示“首页 / 扫描 / 记录”。只有首页、记录是Tab页面；中间扫描与首页“拍照看配料表”共用 `utils/camera.js`，直接通过 `wx.chooseMedia` 的camera模式打开手机摄像头，不再调用条码扫码接口、不先跳介绍页。

只有本次拍摄并确认后、且原生接口返回有效临时照片路径，才进入现有原文核对页进行OCR。取消、空照片或权限失败不导航、不上传、不识别；开始拍摄时清空旧照片，编辑页消费后再次清空，防止重复使用旧图片。

首页小字“扫描商品条码”仍为明确的条码入口，复用 `utils/scanner.js`，本次没有更改它的功能：只展示读取内容，不自动打开二维码链接、不把条码当作配料或商品查询。中间Tab与首页主拍照按钮则走上述摄像拍照OCR流程。旧拍照说明页保留兼容，内部拍照按钮也复用同一拍摄方法。

更改TabBar配置后需完整编译；首次切换custom模式可清除编译缓存。扫码器需在微信开发者工具支持的环境或真机验证，本轮只有自动化替身测试，未操作真机摄像头。

## 数据链路

```text
页面 → utils/records.js → utils/api.js → wx.request
     → Java API → JDBC → 后端 data/snack.mv.db
```

- 上传：点击编辑页确认按钮后，配料文字提交服务端并保存。
- 拍照图片仅上传应用自己的Java后端用于传统OCR，不发送到DeepSeek或其他AI服务、不写入配料记录；未提交文字草稿保存在本机。
- `utils/api.js`：请求超时、会话缓存、并发登录合并、401后只重登重试一次。
- `utils/records.js`：服务端记录增删改查、异步 AI 调研、进度和历史快照查询。
- `utils/storage.js`：草稿持久化，以及旧版本本机记录数据的兼容保留；页面不再从这里读取正式记录。
- 旧版本本机记录不会自动上传，不会被删除。旧草稿若引用原本机记录ID，无法更新为云记录，请复制原文后新建录入。
- 测试设备标识保存在本机；清空微信存储可能生成新的测试用户。正式微信登录使用服务端校验的 openid。

## 上线 / 真机

本机 `127.0.0.1` 只适用于电脑上的开发者工具，手机上的该地址指手机本身。

正式接入需：

1. 后端使用 `prod` 配置，配置 `WECHAT_APP_ID` 和 `WECHAT_APP_SECRET`；生产配置中测试登录接口不存在。
2. 服务部署到 HTTPS 域名，微信后台配置 request 合法域名。
3. 前端 `baseUrl` 改为该域名下的 `/api`，`authMode` 改为 `wechat`。
4. 核对前后端使用相同 AppID；前端通过 `wx.login` 获得临时 code，再由 Java 调微信官方接口校验。
5. 完善隐私保护指引，做权限拒绝、断网、登录失效、重试、记录隔离和真机验收。

## 预览/上传前的包体检查

微信主包有2MB限制。新增图片后先运行 `npm run check:package`：检查会按project.config.json的打包排除规则统计运行文件，超过1.5MB预警线或单张图片超过400KB时列出问题文件，给微信编译留出余量。此检查也包含在现有npm test中，但手动点击开发者工具“预览”不会自动执行npm命令。

静态小插图按实际显示需要等比导出，当前课堂插图最长边512像素；不要把高清原图备份放回小程序目录。测试、脚本、README继续排除打包；OCR语言数据只放后端，不纳入前端。实际最终体积以微信工具上传结果为准，不靠忽略正在使用的图片或删除页面来压包。

## AI 查询与结果页

默认云端服务为DeepSeek，使用官方Search/Fetch与Chat API，模型请求别名 `deepseek-flash` 可配置。不需要本地模型或搜索容器。当前没有使用真实Key完成计费查询验收，不能把模拟测试当成真实结果。

上传原文后直接进入原设计的分组两列解析页，自动开始检索并显示真实结果，不再展示查询设置表单。食品类别移到原文编辑页选填；未填或原文引用未核实时不显示具体限量。返回已有结果不会自动重查，AI结论未经人工审核。

DeepSeek付费模式需 `AI_PROVIDER=deepseek`、`AI_ZERO_COST_ONLY=false`；若遗留为true，会明确阻止调用而非绕过保护。不回退OpenRouter、OpenAI或无AI词表。历史报告标注来源，切换服务后需明确重新解析才付费生成新报告，浏览历史不自动扣费。详见后端 `DEEPSEEK.md`。

## 拍照文字识别

仅补齐既有拍照链路：确认后通过认证的 `/api/ocr/tesseract` 上传至应用后端，由本地RapidOCR（PP-OCRv4）提取文字；路径名保留兼容，回填现有原文框。识字不调用DeepSeek、不需要AI Key、不产生AI API费用。用户核对并点击确认后才开始原有配料分析；没有新增页面、按钮或自动提交功能。失败仍可手动输入，不回填预设内容。

支持JPEG/PNG，单图最多4MB；上传识别超时60秒。生产微信后台需增加后端的uploadFile合法域名，隐私用途说明图片仅用于自有后端OCR。后端OCR语言数据与部署见 `OCR.md`。本机已通过真实包装截图和清晰中英文测试图验证。低可信结果会提示重拍；没有配料标题时提示检查拍摄区域。某些字仍可能误识别，必须人工核对。

## 能力边界

拍照文字识别已接入，结果仍需核对；商品数据库未接入。新调研链路不限制配料名称，也不依赖旧示例知识表。引用来自官方域名不代表AI理解、标准现行性和适用性已核实；不做食品安全评级，不提供个人食用建议，不能以“无资料”判断安全。
